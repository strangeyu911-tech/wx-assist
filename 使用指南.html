作者为什么这么做？

这不是疏忽，是刻意的取舍。原因分两层：

第一层 · 工程常识（与合规无关）

  • 二进制不该进 git：git 永久保存每一次提交的历史。DLL 每次版本更新都提交一份，仓库就永久膨胀，而且删掉也瘦不回来（历史里还在，除非重写历史）。Release 附件是可删可换的外部文件，不随 git clone 下载。这是业界标准做法，不是这个作者的特殊选择。
  • 182 MB 的 ONNX 模型更不可能进 git，这个没有讨论空间。

第二层 · 明确的风险隔离（作者自己写在 .gitignore 注释里）

  • # DLL binaries (closed-source, compliance risk) —— 作者自己承认有合规风险
  • # WASM decryption internals (keys, states, binaries, debug scripts — all local-only) —— 明确标注「仅本地」

关键在于：同一个二进制，放在「git 仓库」里和放在「Release 附件」里，风险完全不同。

放进 git 仓库放进 Release 附件
是否随 clone 下载是，每个克隆者都会拿到否，要主动点下载
是否被代码扫描 / 索引是基本不会
给外界的印象「一个公开的微信解密工具仓库」「一个用了某些组件的应用」
能否事后撤下不能（历史里永远留着）能，随手删
仓库体积永久膨胀且不可逆不受影响

所以作者做的是风险隔离：把「我的原创代码」和「来源不清的敏感二进制」在物理上分开存放。代码保持公开、可审计、可学习；敏感的你自己去拿。

他为此付出的代价：牺牲了开发者体验

README 里明明白白写着「从源码启动桌面应用 / pip install -r requirements.txt / python desktop.py」，但这条路径对「读微信」这部分是不成立的——照做的人一定会卡住，而且报错信息不会告诉你「你缺的是作者故意没给的东西」。

也就是说，作者明知并接受了这个取舍：这份源码保留「可读、可审计」，但不保证「开箱可运行」。理解这一点，你就不会浪费时间怀疑是自己环境配错了。

两条使用路线

🚀 路线 A — 用官方 EXE
从 Releases 下载打包好的可执行文件，双击即用。内置 lib/ 解密组件，功能完整。

适合：只想用功能、不打算改代码。
🔧 路线 B — 从源码运行
Python 后端 + React 前端，改代码即时生效。

适合：想读架构、改功能、二次开发。

已就绪 lib/ 与依赖已补齐，本机可直接启动。
本质区别：这两条路解决的不是同一个问题

路线 A 是「用软件」，路线 B 是「当开发者」。不是「多干一步活」的差别，而是你买到的东西不同——A 买到「今天就能用」，代价是改不了、调不了、升级等作者；B 买到「改代码 → 立即生效 → 能断点调试」，代价是要自己把运行环境凑齐。

所以「哪个更好」取决于你想干嘛：只想拿它干活 → A；想读代码 / 加功能 / 改行为 → B。两者也不冲突，可以都要（但别同时运行——会抢 17327 端口、iLink 会话和 data/ 目录）。

版本现实：最新版没有 EXE 可下

截至 2026-09-11，仓库 tag 已经到 v1.5.1（你的 clone 正好停在这个 tag 上），但 v1.5.1 的 Release 附件数为 0——作者发了版本说明却没上传 EXE。能下载到的最新 EXE 是 v1.5.0，比你的源码落后 11 个提交（内容：公众号即时提醒原文链路修复、Bot 多实例竞态、QQ 消息重复回复等）。

好消息：这 11 个提交完全没有改动 src/wechat/、lib/ 和两个 build.spec。也就是说解密层接口零变动，从 v1.5.0 的 EXE 里提出来的 lib/，喂给 v1.5.1 的源码用是安全的。

这是绝大多数人的正确选择。作者已经把 Python 运行时、全部依赖、以及 lib/ 解密组件都打包进去了。

运行前提

  1. 微信电脑版必须正在运行程序启动时会用 tasklist 检查 WeChat.exe 进程。检查不到就不会自动启动 Bot，界面会是「未运行」状态。所以顺序是：先开微信并登录 → 再启动 wx-assist。
  2. 把 EXE 放在一个有写权限的目录程序会往同级的 data/ 目录写日志、数据库、缓存。别放 C:\Program Files\ 这种需要管理员权限的地方，否则写盘失败。
  3. 建议加杀软白名单PyInstaller 打包的程序常被误报。这是打包工具的通用现象，不是病毒。把 EXE 所在目录加进排除项。
  4. 双击运行首次启动进入引导流程（见下方「首启引导 4 步」）。
单实例保护

EXE 版本用了一个 Windows 全局互斥量 Global\wx-assist-17327。重复双击会弹出提示框「wx-assist 已在运行，无需重复启动」，不会起第二个进程抢端口和数据库。想重启就先把已有窗口关掉。

关闭窗口 = 干净退出

程序注册了 atexit + SIGTERM/SIGINT 处理：关窗口会走 _graceful_shutdown() 优雅停止 Bot、关闭数据库；如果 5 秒内没停干净，会强制杀掉自己的进程兜底。所以你永远不会留下僵尸后台进程。

只想起 Web 服务（不要桌面窗口）

Web 服务器是个 daemon 线程，主线程一退出服务就没了。所以源码模式下必须让主线程保持存活：

set PYTHONPATH=.
.venv\Scripts\python.exe -c "from src.web.server import start_web_server; import time; t = start_web_server(); [time.sleep(1) for _ in iter(int, 1)]"

方法一 · 运行时从临时目录拷（备选）

关键事实：两个 spec 都是 PyInstaller onefile 模式——EXE() 直接吃 a.binaries / a.datas，没有 COLLECT 步骤。onefile 在运行时会把自己解压到 %TEMP%\_MEIxxxxxx\，那个目录里就躺着解压好的 lib/。

  1. 下载精简版 wx-assist_no_rag.exe只有 89.7 MB。别下 255 MB 的完整版——两者的 lib/ 打包内容是逐行一致的，完整版多出来的 165 MB 全是 RAG 模型。
  2. 双击运行，让它停在界面上别关窗口。PyInstaller 退出时会清理临时目录，关早了就没了。
  3. 打开 %TEMP%Win+R 输入 %TEMP% 回车，按修改时间倒序排列，找最新那个 _MEI 开头的目录。
  4. 把里面的 lib\ 整个拷出来复制到 D:\全局项目库\wx-assist\lib\。完成后就可以关掉 EXE 了。
  5. 核对下面这份清单对上了就说明提全了。

ACP 协议本身没有 function-calling 透传，原来的桥接会直接丢弃 tools 参数。本机版本在桥接里加了文本模式工具模拟（acp_bridge.py 的 build_tool_instruction() / parse_tool_calls()）：

  1. 把 OpenAI 的 tools schema 渲染成文字协议塞进 prompt，要求模型想调工具时只输出一个 JSON 信封：{"tool_calls":[{"name":"…","arguments":{…}}]}
  2. 桥接把这段 JSON 解析回来，还原成 OpenAI 格式的 tool_calls 返回给 wx-assist
  3. 工具结果以 <tool_result name="…"> 形式回灌，ReAct 循环照常收敛

剩余的小代价：比原生 function calling 慢一些（每轮都要把工具描述写进 prompt），偶尔可能格式不严格而降级成纯文本——重试即可。

绑定微信推送渠道

这是让成果「送达到你手上」的关键一步。所有提醒、摘要最终都是通过这个渠道推到你微信私聊的。

技术上是 iLink Bot API——一个扫码授权的机器人通道。不操控你的微信窗口，不模拟键盘，纯 HTTP 调用。

绑定流程

  1. 进入「系统配置」→「消息推送」找到「绑定微信 Bot」按钮。
  2. 点击后出现二维码程序调 GET /api/ilink/qrcode 拿到二维码，前端用 QRCodeSVG 渲染。
  3. 用手机微信扫码状态会依次流转：wait（等待扫码）→ scanned（已扫描）→ confirmed（已确认）。前端在轮询 GET /api/ilink/qrcode-status。
  4. 绑定成功凭据写入 data/ilink_account.json，界面上会显示 bot ID 和你的 user ID。
  5. ⚠️ 立刻在微信里给这个 Bot 发一条消息弹窗会提示你这一步，千万别跳过——这是激活推送通道的必要动作，不发消息通道就是死的，后面所有推送都收不到。
  6. 点「发送测试消息」验证如果微信里收到消息，说明链路通了。
第 5 步是最容易踩的坑

文档里明确写了这句：「弹窗提示『请立即在微信中给 Bot 发一条消息』」。很多人扫码成功后就直接去配功能了，结果配了半天一条推送都收不到，回来查半天。扫码 ≠ 通，发消息才算通。

① 关键词提醒

解决的痛点：群里有人问「今晚聚餐去哪吃」，你看到时已经散场了。

原理很直接：监听群消息 → 检测到配置的关键词 → 生成通知，可选立刻推到你微信私聊。

怎么配

  1. 「群聊助手」→ 关键词提醒 → 添加提醒群
  2. 选择群聊从会话列表里挑。注意：一个会话只能属于一个提醒组——如果你选的 chat_id 已经存在于某个组里，系统会自动把关键词合并进去，而不是新建重复行。
  3. 填关键词多个关键词用分隔符隔开，命中逻辑是 OR——任意一个命中就触发。
  4. 选择推送方式勾上「推送到微信」就走 iLink 推到你私聊；不勾就只进通知中心，你需要主动去「群聊助手 → 通知中心」看。

规则行为
匹配方式子串包含，不是分词也不是正则。"bug" in "debug" 这种也会命中，配关键词时注意
大小写不区分（两边都 .lower() 后再比对）
多关键词OR 逻辑，任一命中即触发

机制阈值为什么

通知的三种消费方式

  • A · Web 界面：通知中心里看，点「已读」标记为 delivered，点「忽略」标记为 ignored。
  • B · 外部 Agent 拉取：GET /api/assistant/notifications/pending 取出所有待投递通知，你自己转发到邮件 / 钉钉，处理完调 ack 标记。
  • C · iLink 即时推送：配了 push_target = "ilink" 就直接推到你微信。

通知生命周期：pending →（ack）delivered /（ignore）ignored。超过保留期会自动清理，但只清理非 pending 的——待投递的不会被误删。

② 群聊 AI 摘要

解决的痛点：群太多、消息太多，爬楼爬不动。

核心设计是「分组」：把多个群打包成一个分组，定时生成一份合并摘要（按群分段），你一眼扫完。

怎么配

  1. 「群聊助手」→ 新建摘要分组给分组起个名字（比如「工作群」「家人群」）。
  2. 往组里塞会话一个会话只能属于一个分组。每个会话可以单独开关（分组开着但某个群这轮不摘）。
  3. 设置 cron 表达式决定什么时候摘。语法见下节。
  4. 选回溯窗口两种模式：
    • auto（智能回溯）：从 cron 表达式推导。程序会解析 cron 的小时字段，算出相邻两次执行的间隔，再加 1 小时 buffer。比如你设 0 9,18 * * *，它会知道白天那段要回溯约 10 小时。
    • manual：直接用手填的「回溯小时数」（3 / 6 / 12 / 24）。
  5. 配置群档案（可选）群档案是分组级共用的输出风格配置：行动项优先 / 完整复盘 / 极简速览 / 自定义。想要特殊要求就直接写在自定义 prompt 里。
  6. 开启推送勾上就走 iLink 推到你微信。

cron 语法

标准 5 字段：分 时 日 月 周，周日 = 0。

single内容量小1 次 LLM 调用搞定所有会话，靠 prompt 约定点名各会话
packed（打包）内容量中等1 次 LLM，多会话分节输出。如果 provider 报上下文超限，会就地降级成 per_chat
per_chat（逐会话）内容量大每个会话各调 1 次 LLM（并发 3），然后纯文本拼接。注意：不会再有第 N+1 次汇总调用

每个会话最多取 500 条消息，超出会丢弃最旧的。如果开了「仅摘未读」，会按会话各自切尾部。

群记忆

这是让它越用越准的机制。每次摘要后，AI 会滚动更新该分组的累积记忆（按 ### 会话名 分块存），下次摘要时作为上下文喂回去。所以它能记住「这个群里 A 和 B 在争什么」「上周定了个什么计划」。

  • 记忆是组级单一的（一个分组一份），按 group_id 写回磁盘。
  • 字数上限随会话数放大。
  • 可以手动编辑，走 CAS（memory_rev 版本号）防冲突。
  • 可以整体关闭（memory_enabled = false），关了之后摘要不再更新记忆。
  • 如果全部会话都失败了，会跳过记忆更新——不会把错误信息浓缩进记忆里污染后续结果。
「无新内容」和「报错」是两回事

摘要没新内容时仍会写进通知队列（记录但不推送）。而报错必须推送告知——程序明确禁止用静默协议掩盖错误。所以如果你收到「⚠ 有失败」的筛选提示，说明确实有任务挂了，去「定时任务 → 执行历史」看详情。

技术细节

  • 嵌入模型：BAAI/bge-small-zh-v1.5，中文优化，512 维（fastembed 的 ONNX 量化版实测输出 512 维）
  • 推理：ONNX Runtime，纯本地 CPU，不需要显卡
  • 向量库：ChromaDB，存在 data/chroma，用 cosine 距离

检索流程

你提问 "xxx"
  ↓
1. embed(query)        → 本地 ONNX 推理出向量
2. ChromaDB 粗搜        → 取 top_k × 2 个候选（默认 20 个）
3. 相似度阈值 0.4 过滤   → 丢掉不够相关的
4. rerank             → 取最终前 N 个
5. build_context      → 格式化成文本，回填给 LLM

冷启动索引

首次启动（或索引不存在时）会起一个后台线程，回溯最近 30 天的聊天记录，每批 1000 条地建索引。这就是完整版首次启动要等 1–5 分钟的原因。进度会持久化到 data/rag_state.json，中断了下次能续上。

重启时如果缓存里已有数据，会跳过全量同步，只做增量，所以第二次以后启动很快。

维护

  • 超过 60 天的 chunk 每小时自动压缩清理，不会无限膨胀
  • 微信 4.x 的非文本消息密文（28b52ffd 开头且长于 100 字符的 hex）会被自动过滤，不污染索引

怎么用

⑥ Agent 智能助手

✅ 本机现状：可用（走桥接的文本模式工具模拟）

它是怎么工作的

本质是 LLM + 工具，没有意图分类器——LLM 自己判断要不要调工具、调哪个。跑的是 ReAct（推理-行动）循环：

循环（最多 8 步）:
  1. 把 system prompt + 对话历史 + 工具清单 发给 LLM
  2. LLM 没调工具 → 直接回复，结束
  3. LLM 调了工具 → 执行，把结果作为 Observation 塞回对话
  4. 回到第 1 步

停止条件:
  · LLM 直接回复
  · 8 步用完 → 回 "我还在思考中"
  · 软约束：连续 3 次调同一工具没进展必须停

安全阀：写操作强制确认

这点做得很扎实。所有会改变状态的操作（增删任务、创建技能）在引擎层被硬拦截，不是靠 prompt 软约束——LLM 想绕都绕不过去。

流程：LLM 需要写操作时，先调 confirm_action → 引擎拦截并暂存 → 把确认问题抛给你 → 你回「确定 / 确认 / 好 / 是 / 嗯 / 行 / ok」→ 引擎直接执行刚才挂起的操作（不会让 LLM 重新生成一遍，避免它即兴发挥）→ 放行后续步骤。

  • 回「取消 / 不 / 算了」→ 放弃
  • 回模糊内容 → 原问题重问一遍

Skill 是什么

Skill = 一个可执行的能力单元，存在 data/skills/{name}/SKILL.md。一套 Skill 同时能被定时任务和 Agent 调用，走同一条执行路径。

两种类型：

script 类型
跑一个脚本子进程。适合：调外部 API、抓数据、跑计算。

超时、编码、防黑窗都处理好了。
prompt 类型
一句 prompt 驱动 LLM 跑一次（不保留历史）。适合：需要判断、总结、推理的任务。

SKILL.md 格式示例

---
name: weather
description: 天气预报 — 查询指定城市的天气情况
type: script                    # script | prompt
command: weather.py             # script 类型必填，相对 scripts/ 目录
timeout: 45                     # 超时秒数，默认 30，仅 script 生效
args:
  location:
    type: string
    required: true
    description: 城市名，如 北京、上海、Tokyo
  days:
    type: integer
    default: 2
    description: 预报天数（1-3）
---

prompt 类型则把 command 换成必填的 prompt 字段。

[SILENT] 协议

输出内容 strip() 后恰好等于 [SILENT] 时，调度器跳过推送。这是给监控类任务设计的——比如「盯某个网页有没有更新」，没更新就静默，别打扰你。

错误禁止静默

约定很明确：脚本报错必须用非零退出码 + 打印错误信息，禁止用 [SILENT] 掩盖错误。prompt 类型同理。这样你才能知道任务挂了，而不是以为「它一直没变化」。

内置示例 Skill

「定时任务 → Skill 库」里有一键生成示例的按钮（POST /api/skills?sample=1）：

  • weather（script 型）——查天气，走 wttr.in，免费零配置，失败重试 2 次
  • skill-designer（prompt 型）——技能设计助手，帮你把需求整理成 Skill 方案

创建一个自己的 Skill：推荐流程

  1. 在微信里跟 Agent 描述需求比如「我想要一个每天帮我总结 Hacker News 前 10 条的技能」。
  2. Agent 调 skill-designer 出方案它会给你一份设计。
  3. 你确认不满意就让它改。
  4. Agent 调 create_skill 正式创建这一步需要你确认（写操作）。
  5. 去「定时任务」挂个 cron让它在指定时间跑。

命名限制：名称 2–32 字符，只能用字母、数字、下划线。

手动触发

每个任务旁边有「立即执行」按钮，走完整的执行 + 推送链路（不是 dry-run），执行完会预览前 120 字结果。注意它会真的推送，别在半夜手滑点。

调度参数

调度器每 60 秒 tick 一次（内部 1 秒粒度 sleep，方便快速响应停止指令）；同一任务 2 分钟内不重复触发；任务用线程池执行（最多 3 个并发），不会阻塞 tick。

timeout都工具调用超时秒数，默认 30

配置写错了（缺必填、枚举非法、重名）只会跳过那一个 server 并告警，不影响其他 server 和程序启动。

工具命名与代理机制

外部工具会被命名成 {server}__{tool} 的形式注入 LLM 的 function calling 列表。Agent 完全无感知——它看到的工具清单里本地工具和 MCP 工具混在一起，直接调就行。重名冲突时后者整个跳过并告警。

高可用设计

  • 每 5 秒对每个 server 发一次 ping
  • 连续 3 次失败 → 降级，把该 server 的工具从工具表里摘掉（LLM 不再看到，不会卡死）
  • ping 恢复成功后自动重新 list_tools 并注入，全程不用重启程序
  • 降级是「摘工具」而不是「断连接」，恢复更快
安全措施
  • 环境变量隔离：MCP 子进程不继承程序的敏感环境变量（密钥、DATABASE_URL、DATA_DIR、PYTHONPATH），只透传 PATH
  • 命名空间隔离：server__tool 前缀避免本地 / 外部工具撞名
  • 写操作兜底：外部工具如果涉及写操作，由本地 confirm_action 机制兜底确认
可以直接粘贴 Claude Code 的配置

「MCP 工具」页签的添加弹窗支持 表单 + JSON 粘贴双模式，兼容 Claude Code 的 mcpServers 格式。你已经在用的 MCP 配置可以直接搬过来。

个人自用避坑指南

这一章是本指南最重要的安全结论，先说立场：微信官方在 2024-2026 年连续发布打击"外挂"的公告，本项目用的三类技术手段在官方眼里完全是三种东西。个人自用的最优解只有一句话——能走 iLink 的全部走 iLink，真实账号一行自动发送都不要有。

核心原则：机器人投递优先（官方正门）

绑定微信推送渠道用的 iLink Bot API 是腾讯 2026 年正式开放的官方通道（产品名 ClawBot，ilinkai.weixin.qq.com），有正式使用条款背书，零封号风险。摘要、提醒、公众号速读、Agent 回复——所有成果都应该投递到这个机器人对话里，而不是用你的真实微信账号发到群里。

具体落点：

  • 「群聊 AI 摘要」生成后 → 投递渠道选微信 Bot 私聊，不要选"发送回群"；
  • 「关键词提醒」命中后 → 推送到微信 Bot，你看到提醒后自己手动去群里回；
  • 「公众号实时提醒」→ 同样走 Bot 私聊；
  • 「Agent 智能助手」→ 对话一律发生在 Bot 通道内。
红色区域：真实账号自动发送，建议永远关闭

所有"用你的真实微信账号自动发消息到群聊/私聊"的功能（模拟按键操控微信窗口的那条链路），在微信安全中心 2026 年 1 月公告里被点名归类为"外挂类"：利用模拟按键、自动化脚本等手段操控微信。处罚是阶梯式的：警告 → 限制功能 → 封禁账号，且账号绑定的微信支付、聊天记录、好友关系都在这条船上。

结论：要发的内容你自己手动发。工具负责"让你知道该发什么"，不负责"替你发"。多花的那 10 秒钟，买的是主号的安全。

其他避坑清单
  • 主号隔离：如果一定要尝试高风险功能（不建议），用注册时间久、有实名的小号，主号（聊天 + 支付那个）永远别参与 Hook 和自动化；
  • 只自用，不传播：《微信个人账号使用规范》1.2.5 明确"将用于上述用途的软件运营或向公众传播"是独立加重条款——公开判例里获刑的几乎都是开发/销售方；
  • 拒绝一切"增强插件"：抢红包、批量加好友、虚拟定位、营销群发——哪怕别的项目提供，碰都别碰，这些是封号重灾区+刑事案件高发区；
  • 控制节奏：定时任务别整点批量触发，推送频率保持"像个正常人在看"的水平；
  • 数据合规：导出的聊天记录、朋友圈档案包含他人个人信息，别上传到第三方服务或发给无关的人；
  • 企业场景直接换官方 API：企业微信群机器人 Webhook / 自建应用 / 微信客服，能力完全覆盖推送需求且零风险。"企业内部用"在平台规则面前没有豁免。
风险分级速查

🟢 低风险：iLink Bot 推送（本指南「绑定微信推送渠道」章）、本地 AI 摘要计算、收藏/朋友圈整理浏览。
🟡 中风险：Hook 提取密钥 + 解密直读本地数据库（纯本地只读，对端不可见，但属官方定义的违规获取行为）。
🔴 高风险：模拟按键操控真实账号收发消息（定时群发、自动回复、写群）。
